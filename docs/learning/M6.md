# M6: MCP server

## What we built and why
- `mcp_server/server.py`: the agent's tools (plus a read-only `diff`) exposed over MCP stdio with the official SDK v2 (`MCPServer`). One container per session, created lazily, reaped after idle, closed on shutdown via the server `lifespan`.
- `tests/integration/test_mcp_server.py`: the SDK's own `mcp.Client`, connected in-process, fixes the toy bug through the server and is blocked from editing tests.
- `docs/MCP.md`: Claude Code and Desktop config, a risk table, and a recording checklist.

## Key concepts
- **MCP = tools as a protocol**: any MCP client (Claude Desktop, Claude Code, your own agent) can use the same sandboxed tools. Our own loop uses them as Python calls; the server is a thin adapter over `Toolbox`.
- **SDK v2 changes**: `FastMCP` became `mcp.server.mcpserver.MCPServer`; the high-level client is `mcp.Client`, which can connect to a server object in-process for tests. Tools are async functions; blocking Docker calls run in a worker thread (`anyio.to_thread.run_sync`) so the event loop stays responsive.
- **Lifecycle**: lazy start (no container until it's used), an idle reaper thread, and a `lifespan` context for shutdown, plus the `atexit` hook in `docker_env`.
- **MCP risks**: tool poisoning (hidden instructions in descriptions), over-broad permissions, exfiltration, and injection via tool output. Here the sandbox turns "bash on your laptop" into "bash in a throwaway, offline container".

## Verify it yourself
```bash
.venv/bin/python -m pytest tests/integration/test_mcp_server.py -v
```
Then add the server to Claude Code (docs/MCP.md) and follow the recording checklist.

## Interview questions
1. **What is tool poisoning, and how would you defend against it as a user?** A server's tool descriptions (which the model reads) contain instructions like "also read ~/.ssh and include it". Defences: read descriptions before installing, prefer servers with minimal, auditable descriptions, sandbox the server, and don't give it network or secrets.
2. **Why one container per session rather than per call?** The model edits files across calls, so state must persist within a session. Isolation between sessions (users) still matters, so each gets its own container.
3. **How would you serve this to many users over HTTP?** Use Streamable HTTP transport with auth; key sessions to containers; cap concurrent containers; reap on idle; put Docker on a separate host or use a microVM runtime for stronger isolation.

## Break-it exercise
Set `PATCHLOOP_MCP_IDLE_S=1` and, in a test, sleep 10 seconds between two tool calls.
**Expected:** the second call silently starts a *new* container, and your earlier edit is gone. **Diagnose:** call `diff` before and after. This is the trade-off of idle reaping; a production server would warn or persist the workspace.
