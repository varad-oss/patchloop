# M0: Research, ADRs, scaffold

## What we built and why
- A pinned Python project (`pyproject.toml`), configs for target repos (`config/repos.toml`) and prices (`config/pricing.toml`), CI (`.github/workflows/ci.yml`: ruff + unit tests, no Docker), and ADRs (`docs/DECISIONS.md`).
- Versions were verified rather than remembered. PyPI's JSON API gave versions and licences, and the installed packages were inspected for the exact API. Two things were found by reading the source: MCP v2 renamed `FastMCP` to `MCPServer`, and the Anthropic SDK exposes `usage.output_tokens_details.thinking_tokens`.
- Target repos were chosen by **measuring** test time in the real base image (ADR-004). more-itertools lost because 13.9 s × 2 runs per candidate × hundreds of candidates is too slow.

## Key concepts
- **Pin everything that affects results**: SDK versions, repo commits (not tags), the base image, and pytest version inside the image.
- **Price config with a "checked" date** (`config/pricing.toml`): cost is computed from returned usage × a dated price table, never estimated.
- **CI without Docker**: `@pytest.mark.docker` tests are skipped automatically when the images are missing (`tests/conftest.py`).

## Interview questions
1. **Why pin the commit and not the tag?** Tags can be moved or deleted. A commit hash is content-addressed, so the benchmark's `base_commit` keeps meaning the same code forever.
2. **Why measure test-suite time before choosing a target repo?** Validation runs the suite twice per candidate bug and the grader once per episode. Suite time multiplies through the whole pipeline: 14 s vs 0.4 s decides whether `make bench` takes minutes or hours.
3. **What belongs in an ADR?** The decision, the alternatives, the evidence (measurements, docs read) and the consequences. That way a reviewer can disagree with the reasoning rather than guess at it.
