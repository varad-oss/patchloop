# M2: Sandbox and tools

## What we built and why
- `sandbox/docker_env.py`: one container per episode, every isolation flag from the spec, plus `--init`. Driven through the `docker` CLI via a single choke point, `_run_docker` (ADR-002).
- `agent/tools.py`: `bash`, `view_file`, `search`, `str_replace`, `run_tests`, `submit`, with `structured` and `bash_only` toolsets.
- Tests: `tests/integration/test_sandbox_security.py` (network, read-only tests and root fs, non-root, capabilities, memory, PIDs, timeouts, host isolation, git history) and `tests/unit/test_sandbox_unit.py` (argv assertion, flags, secrets).

## Key concepts
- **Defence in depth**: path checks in Python (`resolve_path`) *and* a symlink check inside the container (`Toolbox._check_real`) *and* the read-only mount *and* the grader's forbidden-path list.
- **Anonymous volume + read-only root**: the workspace is writable but disposable; everything else is immutable (`DockerEnv.run_argv`).
- **Fresh git history** (`DockerEnv.start`): otherwise the answer is one `git diff HEAD` away.
- **Stateless bash** (fresh `docker exec` per call, as in mini-SWE-agent): no hidden shell state to corrupt, easy to replay. The cost is that `cd` doesn't persist, which the tool description tells the model.
- **Truncation with an explicit marker**: the model must know output was cut, or it will reason from a partial view.
- **Host-side text, sandbox-side execution**: `str_replace` reads the file through `docker exec cat`, edits the string in Python, and writes it back through `docker exec -i ... cat >`. Nothing agent-authored runs on the host.

## Interview questions
1. **What can a malicious repo do to the agent's host?** Nothing directly: commands run in a container with no network, no capabilities, as non-root, with a read-only root filesystem and resource limits. The remaining risks are container-escape kernel bugs (mitigated by keeping Docker updated, or gVisor/Firecracker for stronger isolation) and resource exhaustion of the Docker VM (limited by memory, CPU and PID caps).
2. **Why make tests read-only instead of trusting the prompt?** Reward hacking: an optimiser that is graded by tests will eventually edit the tests. A mount flag is enforcement; a prompt is a request. The grader additionally rejects diffs touching `conftest.py` and pytest config, which can change outcomes without touching test files.
3. **Why did the PID-limit test break other tests, and what fixed it?** Forked children outlived the command (`timeout` only kills its direct child), held the container's 256 PIDs, and made later `docker exec` calls fail with "Resource temporarily unavailable". The fix: give that test its own container and add `--init` so orphans are reaped once they exit.

## Break-it exercise
Remove `readonly` from the tests `--mount` in `DockerEnv.run_argv`, then run `pytest -m docker -k read_only`.
**Expected:** `test_tests_are_read_only` fails because the write succeeds. **Diagnose:** run `docker inspect <container> --format '{{json .Mounts}}'` on a live episode container and check `"RW": true` on the tests mount. Restore the flag.
