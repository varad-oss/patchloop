# M5: Experiments (not yet run)

E1 and E2 need an API key and your approval of the pilot cost. Nothing below is a result. This note is how to run
the experiments and how to read them.

## What to run
1. **Effort (ADR-008)**: `patchloop eval --run-id effort-low --effort low --limit 5 --pilot`, and the same with `medium`. Compare resolve rate and cost on the same 5 tasks; pick one and record it.
2. **E1 baseline**: `make eval-pilot RUN=E1`. Read the printed cost per task and the extrapolated total. If it's acceptable, run `make eval RUN=E1`.
3. **E2 interface ablation**: same with `TOOLSET=bash_only`.
4. `patchloop report --all`, then read `docs/EVAL_REPORT.md` and `results/E1/viewer.html`.

## How to read the results
- Compare E1 and E2 with intervals, and also **per task** (the same 36 tasks). A paired view (tasks where only one condition succeeded) is more sensitive than two independent rates.
- Look at the failure classes. If `never_found_the_bug` dominates, the bottleneck is localisation (search/view tools, prompts). If `wrong_fix` dominates, it's reasoning.
- Check `cache_read_tokens`: if it's 0 across steps, something in the prefix is changing (see ADR-001).
- Check `episodes_with_compaction`: at 40 steps it should be rare. Frequent compaction means observations are too large.

## Interview questions
1. **What would you expect from a bash-only vs structured toolset, and why?** Structured tools give smaller, more predictable observations (numbered views, unique-match edits with error counts), which helps weaker models. Strong models often do as well with bash alone (SWE-agent's ACI paper vs mini-SWE-agent). That makes it a model-dependent empirical question, and the reason E2 exists.
2. **How do you choose an effort level?** Measure on a sample of your own tasks: cost per *completed* task, not per request. Lower effort can need more steps, which can cost more overall.
3. **How do you avoid fooling yourself with an eval?** Fix the task set and seeds before looking at results; report intervals; read trajectories (not just the score); check the oracle resolves 100%; never tune prompts on the full test set without a held-out split.

## Break-it exercise
Run the pilot with `--max-cost 0.001`.
**Expected:** every episode stops with `cost_limit` after one or two steps. **Diagnose:** `stop_reasons` in `results/<run>/summary.json`, and the per-step `cost_usd` in a trajectory. This is how you'd catch a wrong price table before a big run.
