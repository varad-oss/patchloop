# M3: Benchmark generator

## What we built and why
- `benchgen/mutators.py` (strategy A, 7 operators), `benchgen/llm_rewrite.py` (strategy B, opt-in), `benchgen/validate.py` (Workbench), `benchgen/issues.py` (report writers + leak check), `benchgen/build.py` (pipeline). Output: 36 tasks in `bench/tasks/`.
- **Why inject bugs instead of using SWE-bench?** Cheap, fast (sub-2-second suites), fully controlled ground truth, and new bugs the model can't have memorised. The price is realism: these are single-site synthetic bugs.

## Key concepts
- **Span splicing** (`mutators._splice`): mutate one AST node, `ast.unparse` only that node, and paste it over the node's exact column span. The rest of the file keeps its formatting, so the diff is one line. Column offsets are UTF-8 *byte* offsets.
- **FAIL_TO_PASS / PASS_TO_PASS** (`Workbench.try_candidate`): baseline-passing tests that fail with the bug, and the rest, which must still pass. Two runs must agree exactly (no flaky tasks). Candidates are rejected if they break more than 25% of the suite (usually an import-time crash, which is a boring bug).
- **Diversity**: round-robin over operators, and at most one bug per function (`build.build`).
- **Leak check** (`issues.leak_check`): the report must not name the file, line or changed code. The excerpt (`issues.failure_excerpt`) keeps only test-file frames and `E` lines, because library frames would print the buggy line.
- **Difficulty tags** (`build.difficulty`): strategy, operator, number of failing tests, lines changed, whether the buggy function is named in a failing test.

## Interview questions
1. **How do you know a generated task is solvable and well-posed?** It's validated: the original passes, the mutation fails specific tests deterministically, and the oracle (reverse patch) resolves it through the real grader. That last check proves the harness, not just the generator.
2. **How can a benchmark leak the answer?** Through the issue text (file names, line numbers, code), the environment (git history, `.orig` files, pip caches), or the tests themselves. PatchLoop handles the first with the leak check and the second with fresh git history; the third is inherent in giving the agent failing tests.
3. **What's the contamination risk, and how would you reduce it?** The models have seen toolz and boltons, so they may recognise "this isn't how upstream wrote it". To reduce it: use less popular or private repos, rewrite whole functions (strategy B), or compare against a held-out set of post-cutoff repos.

## Break-it exercise
In `issues.failure_excerpt`, drop the frame filter so every `path:line: in` frame is kept, then run `make bench` on toolz with `--target 5`.
**Expected:** many candidates are now "rejected by leak check: mentions file itertoolz.py" (the library frames print the file). **Diagnose:** grep `results/bench.log` for `rejected`. This shows why filtering, not just checking, is needed.
